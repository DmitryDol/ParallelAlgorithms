## Два варианта ускорения (делаем оба)

Трактовка задания пока не подтверждена (вопросы 1–3 в [README.md](../README.md#вопросы-преподавателю)), поэтому
оба варианта считаются из одних и тех же замеров:
- **Вариант А — «флаг компиляции»:** одна программа, разные сборки; $S_А(N) = T_{\text{без флага}} / T_{\text{с флагом}}$
  → `results/speedup_flags.png`. Дополнительно — вклад векторизации и `-ffast-math`
  → `results/speedup_vectorization.png`.
- **Вариант Б — «блочный против точечного»:** одна сборка, два режима; $S_Б(N) = T_{\text{точечный}} / T_{\text{блочный}}$
  → `results/speedup_block.png`; выбор размера блока → `results/time_vs_block.png`.

Сборки (одни и те же исходники, отличаются только ключами):

| Сборка | GCC / Clang | MSVC |
|---|---|---|
| `noopt` — без флага | `-O0` | `/Od` |
| `opt` — с флагом | `-O3 -march=native` | `/O2 /arch:AVX2` |
| `opt_novec` — с флагом, без векторизации | `-O3 -march=native -fno-tree-vectorize` | `/O2` (без AVX2: штатно отключить векторизацию в MSVC нельзя) |
| `opt_fastmath` — с флагом и перестановкой операций | `-O3 -march=native -ffast-math` | `/O2 /arch:AVX2 /fp:fast` |

Ключи типов сборки CMake (Debug/Release) очищены: уровень оптимизации задаёт только сборка.

## Всё одной командой

После любого изменения или на новом компьютере (из корня репозитория):

```bash
uv run python lab2_cpp/run_all.py
```

Скрипт по очереди: настраивает и собирает C++ (CMake), запускает тесты C++ (CTest) и сверку с этапом 1, делает все
замеры (`bench.py`), строит графики (`plot_speedup.py`) и собирает черновик отчёта (`report/make_report.py`). Старые
`results/` и отчёт перезаписываются целиком. Варианты: `-G Ninja` — генератор CMake при первой сборке;
`--skip-bench` — не перемерять (например, после правки текста отчёта); параметры `bench.py` (`--sizes`, `--block`,
`--repeats`) передаются как есть. В контейнере всё вместе занимает около 3 минут.

**Почему через `uv`, если этап на C++.** Всё, что измеряется, — разложение и замер времени — делает программа на C++
`cholesky_<сборка>`: она сама засекает время (`std::chrono::steady_clock`) вокруг разложения. Python только запускает
её с разными $N$ и ключами, собирает её вывод в CSV, рисует графики и собирает отчёт; на измеренное время он не
влияет. Программу можно запускать и напрямую, без Python, — так её и показывать на защите
(`lab2_cpp/build/cholesky_opt -n 1000 -b 32`, в Visual Studio — `lab2_cpp\build\Release\cholesky_opt.exe`).

## Сборка и запуск по шагам

**Linux** (или WSL):

```bash
cmake -S lab2_cpp -B lab2_cpp/build
```
```bash
cmake --build lab2_cpp/build
```
```bash
ctest --test-dir lab2_cpp/build
```

**Windows.** Вариант 1 — MinGW-w64 из MSYS2 (те же ключи, что в Linux): в терминале MSYS2 UCRT64 установить
`pacman -S mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja`, затем те же три
команды с `-G Ninja` в первой. Вариант 2 — Visual Studio 2022 (MSVC), из «Developer PowerShell»:

```bash
cmake -S lab2_cpp -B lab2_cpp/build
```
```bash
cmake --build lab2_cpp/build --config Release
```
```bash
ctest --test-dir lab2_cpp/build -C Release
```

Сборка под Windows в контейнере не проверялась (проверены GCC 13 и Clang 18 в Linux); если что-то не соберётся —
прислать текст ошибки.

**Программа** (на сдаче преподаватель может задать любые $N$ и $b$; $N$ не обязано делиться на $b$):

```bash
lab2_cpp/build/cholesky_opt -n 500 1000 2000 -b 32
```

Параметры: `-n` — размерности, `-b` — размер блока (32), `-m point|block|both` — режим, `-r` — число замеров,
`--csv` — вывод в CSV, `--dump FILE` — выгрузить $L$, `--info` — ключи сборки и компилятор, `-h` — справка.
Неверные аргументы — сообщение и код возврата 2; погрешность больше $10^{-9}$ — код возврата 3.

**Сверка с этапом 1, замеры, графики** (из корня репозитория):

```bash
uv run pytest
```
```bash
uv run python lab2_cpp/bench.py
```
```bash
uv run python lab2_cpp/plot_speedup.py
```

`bench.py` по умолчанию проходит $N = 64 \dots 2048$ (степени двойки и промежуточные точки ×1,5) и подбирает $b$
при $N = 1024, 2048$; другие значения — `--sizes`, `--block`, `--blocks`. Каждая точка меряется не меньше `-r` раз
(3), а короткие разложения — пока замеры суммарно не займут 1 с (`--min-total`).
Перед итоговым замером закрыть лишние программы, ноутбук — от сети, режим «максимальная производительность».

## Результаты (предварительно, облачный контейнер)

Сейчас в `results/` — прогон в облачном контейнере: Intel Xeon (виртуальная машина, AVX-512, L1d 48 КБ и L2 2 МБ
на ядро), Linux, GCC 13.3. Для отчёта `bench.py` и `plot_speedup.py` нужно перезапустить на компьютере из отчёта:
файлы перезапишутся целиком.

- **Вариант А** ($b = 32$): у блочного алгоритма $S_А$ растёт с 4,3 при $N = 64$ до 6,6–7,1 при $N \geq 384$;
  у точечного, наоборот, падает с 7,1 до 3,7: при больших $N$ оптимизированный точечный код упирается в память,
  и флаг перестаёт помогать.
- **Вариант Б:** в сборке с флагом $S_Б$ растёт с 0,55 при $N = 64$ до 1,8–2,0 при $N \geq 1024$ — блоки начинают
  выигрывать, когда матрица перестаёт помещаться в кэш. В сборке без флага $S_Б \approx 0{,}9 \dots 1{,}04$:
  неоптимизированный код ограничен лишними командами, а не памятью, и блочность ему не помогает.
- **Векторизация:** без неё блочный алгоритм медленнее в 1,35 раза, точечный — в 1,7; `-ffast-math` ускоряет
  ещё в 1,6 (блочный) и 1,9–2,5 раза (точечный).
- **Размер блока:** время почти одинаково при $b = 24 \dots 48$ (различия до 2 %), выбран $b = 32$.
- **Производительность:** блочный алгоритм с флагом — до 6,6 GFLOP/s (точечный — 7,1 при малых $N$ и 3,3 при
  больших), с `-ffast-math` — до 11,2 (точечный — до 12,9, пока матрица в кэше), без флага — около 0,9–1,0.
  Время растёт как $N^3$.
- **Погрешность** во всех сборках того же порядка, что на этапе 1 ($2{,}3 \cdot 10^{-14}$ при $N = 2048$).

## Журнал

1. **Форма данных.** Матрицы — один массив `std::vector<double>` по строкам. Блок $\tilde A_{ij}$ вычисляется
   на месте $L_{ij}$ (у диагонального блока — только нижний треугольник), поэтому временные буферы не нужны;
   на этапе 3 это даст «одного писателя» на блок. Блоки $k < j$ всегда полные, неполным бывает только последний.
   Точечный режим — та же форма скалярных произведений (jik) без блоков.
2. **Ядро на указателях, без классов-обёрток:** при `-O0` вызов функции на каждое обращение к элементу раздул бы
   разницу между сборками за счёт абстракций, а не алгоритма. Внутренний цикл — одна функция `dot`.
3. **TDD.** Тесты написаны до реализации, на заглушках упали по ожидаемым причинам. Граничные случаи в тестах:
   $N = 1, 2$; $N < b$; $N = b$; $N$ кратно и не кратно $b$; простые $N$ (7, 13, 37); $b = 1$; $b \geq N$;
   не СПО-матрица; неверные аргументы. 12 намеренных порч кода — все роняют тесты. Порчу «строка $i$ вместо строки
   $j$» в точечном Холецком блока тестовая матрица не замечает (все её внедиагональные элементы равны $1/3$),
   ловят тесты на случайных СПО-матрицах.
4. **Сверка с этапом 1:** $L$ совпадает с эталоном с точностью $10^{-13}$ во всех сборках и режимах (40 случаев,
   GCC и Clang). Между собой сборки без `-ffast-math` расходятся не более чем на 1–2 последних разряда
   ($\leq 4{,}4 \cdot 10^{-16}$), и только в блочном режиме. Причина проверена: GCC при `-march=native` сливает
   $a \cdot b + c$ в FMA; с `-ffp-contract=off` все сборки дают $L$, побитно совпадающую с `-O0`.
   С `-ffast-math` расхождение до $4 \cdot 10^{-15}$.
5. **Векторизация скалярного произведения** (по ассемблеру GCC 13): без `-ffast-math` — «по порядку» (`vmulpd` +
   последовательные `vaddsd`), с ним — частичные суммы в векторном регистре (`vfmadd231pd`). Отчёт компилятора
   в обоих случаях пишет «loop vectorized». Теория (п. 4.4) исправлена.
6. **$N$ — степень двойки:** при $N = 2048$ блочный алгоритм даёт 6,43 GFLOP/s против 6,85 при $N = 2000$ и 2100
   (конфликтные промахи кэша). Поэтому в ряд $N$ добавлены промежуточные точки.
7. **Выброс в замерах.** При повторном прогоне в контейнере у сборки без флага при $N = 256$ все три замера попали
   на кратковременный провал производительности виртуальной машины (8,1 мс вместо 6,2), и на графике появился
   ложный пик ускорения 8,7. Причина — три замера по ~60 мс укладывались в 0,2 с. Исправлено в программе: короткие
   замеры повторяются, пока суммарно не займут 1 с (не меньше `-r` раз), в CSV пишется фактическое число замеров.
8. **Черновик отчёта** генерируется из результатов (`report/make_report.py`) на основе файла отчёта этапа 1;
   проверен валидатором схемы docx, формулы проверены обратным чтением через pandoc (84 формулы).
9. **Не сделано:** итоговые замеры на компьютере из отчёта (кэш на ядро там меньше: L2 256 КБ, поэтому вариант Б
   должен выигрывать при меньших $N$), проверка сборки в Windows, ответы преподавателя на вопросы 1–3.
