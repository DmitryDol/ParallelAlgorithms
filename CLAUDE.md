**Вариант 3: блочный метод Холецкого через блочные скалярные произведения** — разложение $A = LL^T$
симметричной положительно определённой матрицы.

## Как писать код

Любая работа с кодом, тестами, скриптами замеров и графиками — по скиллу **`lab-mode`**
(`.claude/skills/lab-mode/SKILL.md`, адаптация ub-mode): TDD, обязательные граничные случаи, сверка результатов
с предыдущим этапом, чистое вычислительное ядро, журнал решений в README этапа, маленькие коммиты.
Перед началом такой работы загрузить этот скилл.

## Команды

```bash
uv sync                                                  # окружение

uv run python lab3_openmp/run_all.py      # этап 3 целиком: сборка, тесты, сверка, замеры (P = 1…), графики, отчёт

uv run python lab4_mpi/run_all.py         # этап 4 целиком: сборка, тесты (и под mpiexec), сверка, замеры, графики, отчёт
```

Зависимости добавлять через `uv add` (не pip). Для C++ (этапы 2–4) — CMake, C++17; код должен собираться
и в Windows (MSVC или MinGW; MPI — MS-MPI), и в Linux (GCC/Clang; Open MPI/MPICH).

## Инварианты для всех этапов

- **Алгоритм один и тот же:** блочный left-looking (блочная jik-форма) через блочные скалярные произведения:
  для каждого блочного столбца $j$: $\tilde A_{jj} = A_{jj} - \sum_{k<j} L_{jk}L_{jk}^T$ → точечный Холецкий;
  для $i > j$: $\tilde A_{ij} = A_{ij} - \sum_{k<j} L_{ik}L_{jk}^T$ → $L_{ij} = \tilde A_{ij} L_{jj}^{-T}$.
  Не заменять на right-looking/outer-product форму — это другой вариант задания.
- **В C/C++ все операции — своими циклами**, без BLAS/LAPACK (иначе флаги компиляции и распараллеливание ничего не
  меняют). Готовые библиотеки — только как эталон для проверки.
- **Тестовая матрица** — аналитическая, как в `lab1_python/cholesky_ref.py::generate_test_matrix`:
  $L_{ii} = 2$, $L_{ij} = 1/3$ ($i > j$); $A_{ii} = 4 + i/9$, $A_{ij} = 2/3 + \min(i,j)/9$. На каждом этапе печатать
  погрешность $\max|L^{числ} - L^{точн}|$ — ускорение не должно «покупаться» ошибкой.
- **$N$ и $b$ задаются из командной строки**: преподаватель может поменять размерность прямо на сдаче.
  $N$ не обязано делиться на $b$ (последний блок меньше).
- В C/C++ матрица — один непрерывный массив по строкам (`a[i * n + j]`), не `vector<vector<double>>`.
- Замер времени — только самого разложения (`std::chrono::steady_clock`, `omp_get_wtime`, `MPI_Wtime`; не `clock()`),
  несколько повторов, в CSV — минимум и медиана.

## Измерения и железо

- Итоговые замеры делаются на машине, характеристики которой указываются в отчёте (таблица в отчёте строится
  из `results/platform.txt`). Этапы 2–4 меряются на компьютере пользователя: Intel Xeon E5-2678 v3 (Haswell,
  AVX2 + FMA), 12 ядер / 24 логических процессора, 2,5 ГГц, L1d 32 КБ и L2 256 КБ на ядро, L3 30 МБ, Windows 11,
  MSVC 19.51 (Visual Studio). Отчёт этапа 1 сделан на другом компьютере (однокурсника: 4 ядра / 8 потоков,
  4,2 ГГц, Windows 11) — для этапа 1 это не важно, он не про время. Облачный контейнер Claude (4 vCPU, Linux,
  GCC) подходит для отладки, но не для графиков в отчёт.
- MSVC и GCC ведут себя по-разному (без `/fp:fast` MSVC не векторизует скалярное произведение, нет FMA): тексты
  отчётов, которые генерируются скриптами, должны учитывать компилятор из результатов, а не быть написаны под один.
- Размерности $N$ — степени двойки — дают провалы производительности блочного алгоритма (конфликтные промахи кэша);
  подбирать параметры (размер блока) на таких $N$ нельзя.
- Рядом с результатами фиксировать платформу, компилятор и его версию, флаги, число потоков/процессов.
- Итоговые замеры — при закрытых фоновых программах: на этом компьютере они занижали ускорение в 1,2 раза при
  $P = 8$, в 1,5–1,7 раза при $P = 12$ и в десятки раз при $P = 24$ и малых $N$ (проверка и перемер 09.11.2026,
  `lab4_mpi/README.md`). При $P$, равном числу логических процессоров, программа MPI (MS-MPI ждёт активным опросом)
  эпизодически обваливается и при закрытых программах.
- Погрешности в последних разрядах зависят от платформы и библиотек (порядок суммирования, FMA) — это нормально.
- MPI: у пользователя — MS-MPI (`msmpisetup.exe` + `msmpisdk.msi`); в облачном контейнере ставить Open MPI
  (`apt-get install openmpi-bin libopenmpi-dev`): MPICH 4.2.0 из Ubuntu 24.04 под своим `mpiexec` запускает
  независимые процессы с `size = 1`. Open MPI под root и при $P$ больше числа ядер требует ключей — их добавляют
  скрипты этапа 4 (`lab4_mpi/programs.py`).

## Стиль

- Документация, комментарии в коде, подписи графиков — на русском; идентификаторы — на английском.
- Графики — matplotlib в стиле графика этапа 1: ось $N$ в логарифмическом масштабе по основанию 2, сетка, подписи
  на русском, `dpi=200`, сохранение в `results/` своего этапа.
- В `THEORY.md` каждого этапа — определения, формулы с выводами и раздел «Типовые вопросы на защите». При реализации
  этапа дополнять его тем, что реально получилось (числа, выбранные директивы, схема обменов).
- Работа ведётся в ветке `main`.

## Вопросы преподавателю и варианты реализации

Неоднозначные места задания собраны в `README.md`, раздел «Вопросы преподавателю» (пользователь задаст их на сдаче
ЛР 1 и впишет ответы туда же). Пока ответа нет, **каждая трактовка реализуется отдельно** — своя сборка или
программа, свой CSV и свой график; в отчёт идёт то, что подтвердит преподаватель:
- этап 2: ускорение от флага компиляции (одна программа, сборки без флага и с флагом) и ускорение блочного
  алгоритма относительно точечного (`lab2_cpp/README.md`);
- этап 3: директивы OpenMP над циклами и автопараллелизация компилятором (`lab3_openmp/README.md`);
- этапы 3–4: оба определения ускорения — относительно той же программы на одном потоке/процессе ($T_1$)
  и относительно последовательной программы этапа 2 ($T_{посл}$).
Когда ответ получен — записать его в `README.md`; основным в отчёте становится подтверждённый вариант, второй
остаётся дополнительным (его не удалять — «на всякий случай»).
