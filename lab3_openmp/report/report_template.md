# Постановка задачи

Рассматривается та же задача, что и в лабораторных работах № 1 и 2: разложение Холецкого $A = LL^T$ вещественной симметричной положительно определённой матрицы $A \in \mathbb{R}^{N \times N}$, где $L$ — нижнетреугольная матрица с положительными диагональными элементами. Используется блочный метод Холецкого через блочные скалярные произведения.

Цель этапа — распараллелить программу этапа 2 для многоядерного процессора с общей памятью средствами OpenMP, используя лишь автоматическое распараллеливание, и исследовать зависимость ускорения от размерности задачи $N$ и от числа потоков $P$. Слова «автоматическое распараллеливание» допускают две трактовки, поэтому исследованы обе:

1. вариант А — директивы OpenMP над циклами: программист указывает, какой цикл выполнять параллельно (`#pragma omp parallel for`), а создание потоков, распределение итераций между ними и синхронизацию выполняет среда OpenMP;
2. вариант Б — автоматическое распараллеливание компилятором без директив: компилятор сам ищет циклы с независимыми итерациями (<<autopar_flags>>).

Ускорение вычисляется в двух определениях, эффективность — по относительному ускорению:

$$S_{\text{отн}}(N, P) = \frac{T_1(N)}{T_P(N)}, \qquad S_{\text{абс}}(N, P) = \frac{T_{\text{посл}}(N)}{T_P(N)}, \qquad E(N, P) = \frac{S_{\text{отн}}(N, P)}{P},$$

где $T_P$ — время параллельной программы на $P$ потоках, $T_1$ — время той же программы на одном потоке, $T_{\text{посл}}$ — время последовательной программы этапа 2 (без OpenMP, с теми же ключами оптимизации).

## Тестовая задача

Как и на этапах 1 и 2, используется матрица с известным точным фактором Холецкого (индексация $i, j = 0, \ldots, N - 1$):

$$L^{\text{точн}}_{ij} = \begin{cases} 2, & i = j, \\ 1/3, & i > j, \\ 0, & i < j, \end{cases} \qquad A_{ij} = \begin{cases} 4 + i/9, & i = j, \\ 2/3 + \min(i, j)/9, & i \neq j. \end{cases}$$

Погрешность вычисляется в чебышёвской норме:

$$e(N) = \max_{0 \leq i, j < N} \left| L^{\text{числ}}_{ij} - L^{\text{точн}}_{ij} \right|.$$

Она выводится при каждом замере, чтобы убедиться, что ускорение не получено ценой потери точности.

# Программная реализация

## Алгоритм и его параллелизм

Вычислительное ядро этапа 2 не изменилось: матрицы хранятся одним непрерывным массивом по строкам, блок $\tilde{A}_{ij} = A_{ij} - \sum_{k<j} L_{ik} L_{jk}^T$ вычисляется на месте блока $L_{ij}$, все операции выполняются собственными циклами (без BLAS и LAPACK), основная операция — скалярное произведение. Число блоков по каждой размерности $p = \lceil N / b \rceil$.

```
for (jb = 0; jb < p; ++jb) {           // блочный столбец j
  modify(jb, jb);                      // At_jj = A_jj - sum_k L_jk * L_jk^T
  factor(jb);                          // L_jj * L_jj^T = At_jj
  for (ib = jb + 1; ib < p; ++ib) {    // блоки ниже диагонали
    modify(ib, jb);                    // At_ij = A_ij - sum_k L_ik * L_jk^T
    solve(ib, jb);                     // L_ij * L_jj^T = At_ij
  }
}
```

Шаг $j$ использует блоки всех предыдущих столбцов, поэтому цикл по $j$ выполняется последовательно. На шаге $j$ блоки $L_{ij}$, $i > j$, независимы: каждый вычисляется из уже готовых блоков $L_{ik}$, $L_{jk}$ ($k < j$) и $L_{jj}$ и записывается ровно одной итерацией. Поэтому цикл по $i$ можно выполнять параллельно — без гонок данных и без синхронизации внутри цикла. Цикл по $k$ не распараллеливается: это суммирование в один блок (редукция), и параллельное суммирование изменило бы порядок сложений. Внутренние циклы по элементам блока — слишком мелкое зерно: накладные расходы на запуск потоков сравнимы с работой.

Последовательная часть шага $j$ — модификация и разложение диагонального блока. У диагонального блока вычисляется только нижний треугольник: на шаге $j$ это около $j b^3$ операций, всего $\approx N^2 b / 2$; разложения блоков добавляют $\approx N b^2 / 3$. При общей работе $N^3 / 3$ доля последовательной работы

$$\alpha_{\text{block}} \approx \frac{N^2 b / 2}{N^3 / 3} = \frac{1{,}5\, b}{N}.$$

Модификации всех блоков столбца, в том числе диагонального, не зависят от $L_{jj}$, поэтому их можно выполнить вместе в одном параллельном цикле; последовательным остаётся только разложение блока $b \times b$:

$$\alpha_{\text{phases}} \approx \frac{N b^2 / 3}{N^3 / 3} = \frac{b^2}{N^2}.$$

## Вариант А: директивы OpenMP

Реализованы две стратегии, которые отличаются только расстановкой директив:

```
// block: для каждого столбца j
modify_block(jb, jb); factor_block(jb);      // последовательно
#pragma omp parallel for schedule(static)
for (int ib = jb + 1; ib < p; ++ib) {
  modify_block(ib, jb);
  solve_block(ib, jb);
}

// phases: для каждого столбца j
#pragma omp parallel for schedule(static)
for (int ib = jb; ib < p; ++ib)              // включая диагональный блок
  modify_block(ib, jb);
factor_block(jb);                            // последовательно: блок b x b
#pragma omp parallel for schedule(static)
for (int ib = jb + 1; ib < p; ++ib)
  solve_block(ib, jb);
```

Неявный барьер в конце каждого `parallel for` гарантирует, что столбец $j$ готов до начала шага $j + 1$. Указание `schedule(static)` делит $m$ итераций шага на $P$ непрерывных порций по $\lceil m/P \rceil$ или $\lfloor m/P \rfloor$ итераций: внутри шага блоки одинаковы по стоимости (кроме последнего, неполного). Других директив, ручного распределения работы и явной синхронизации нет. Проверка положительной определённости (исключение при отрицательном подкоренном выражении) выполняется только в последовательной части, поэтому исключение не может покинуть параллельную область. Число потоков задаётся параметром командной строки `-t` (функция `omp_set_num_threads`) или переменной окружения `OMP_NUM_THREADS`.

## Проверка правильности

Правильность проверена автоматическими тестами. Тесты этапа 2 выполняются для обеих стратегий: точечное разложение блока и решение треугольной системы на случайных матрицах, блочный алгоритм на тестовой матрице при $N = 1, 2, 3, 5, 7, 8, 13, 64, 100, 129$ и $b = 1, 2, 3, 4, 8, 16, 200$, отказ на матрице, не являющейся положительно определённой, и на некорректных аргументах командной строки. Добавлена проверка распараллеливания: при $P = 2, 3, 5, 8$ фактор $L$ **побитно** совпадает с полученным на одном потоке — в том числе когда потоков больше, чем блочных строк ($N = 40$, $b = 16$, $p = 3$), и когда $P$ не делит $p$ ($N = 129$, $b = 16$). Любая гонка данных или неверная синхронизация нарушила бы это совпадение: четыре намеренно внесённые ошибки распараллеливания (гонка при разложении диагонального блока, неверный порядок фаз, параллельный цикл по зависимым столбцам, пропуск модификации диагонального блока) обнаруживаются тестами. Кроме того, фактор $L$ всех сборок поэлементно сравнивался с результатом эталонной программы этапа 1 (расхождение не превышает $10^{-13}$), а выгрузки $L$ программы OpenMP при $P = 1, 2, 3, 4, 7$ и последовательной программы совпадают байт в байт.
