## 1. Параллельные архитектуры

**Классификация Флинна:** SISD (обычный последовательный процессор), SIMD (одна команда — много данных:
векторные регистры, этап 2), MISD (практически не встречается), MIMD (много независимых потоков команд:
многоядерные процессоры и кластеры — этапы 3 и 4).

**По организации памяти:**
- **общая память** (SMP/UMA — одинаковое время доступа для всех ядер; NUMA — у каждого процессора «своя» более
  быстрая память). Все потоки видят одно адресное пространство → OpenMP, этап 3;
- **распределённая память**: у каждого узла своя память, обмен — сообщениями → MPI, этап 4.

**Многоядерный процессор:** у каждого ядра свои L1 и L2, L3 общий. Когерентность кэшей поддерживается аппаратно
(протокол MESI): если одно ядро записало строку кэша, её копии у других ядер становятся недействительными.

**Hyper-Threading (SMT):** одно физическое ядро выполняет два аппаратных потока, разделяя исполнительные устройства.
Для вычислительно плотного векторизованного кода второй поток на ядре почти ничего не даёт: на 4 физических ядрах
и 8 логических процессорах ускорение обычно упирается в $\approx 4$.

**Процесс и поток:** процесс — программа со своим адресным пространством; потоки — независимые ветви исполнения
внутри процесса с общей памятью (у каждого свой стек и регистры).

## 2. OpenMP

**Что это:** стандарт (API) параллельного программирования для общей памяти — директивы компилятора
`#pragma omp …`, функции библиотеки времени выполнения `omp_…()` и переменные окружения `OMP_…`.
Первая версия — 1997 г., актуальные — 5.2 (2021) и 6.0 (2024). Если компилировать без поддержки OpenMP,
директивы игнорируются и получается исходная последовательная программа — распараллеливание можно
вводить постепенно.

**Модель fork–join:** программа выполняется одним (главным) потоком; на входе в параллельную область
`#pragma omp parallel` создаётся команда потоков (fork), на выходе — неявный барьер и продолжение одним потоком (join).

**Распределение работы:**
- `#pragma omp for` — итерации следующего цикла делятся между потоками команды; `parallel for` — параллельная
  область + распределение цикла в одной директиве;
- `sections`, `single` (выполняет один поток), `master`/`masked`;
- `task` (+ `depend`) — задачи с зависимостями (OpenMP ≥ 3.0/4.0) — это уже не «автоматическое» распараллеливание.

**Расписание** `schedule(kind, chunk)`:
- `static` — итерации делятся на равные порции заранее (минимальные накладные расходы, хорошо при одинаковой
  стоимости итераций);
- `dynamic` — свободный поток берёт следующую порцию (балансирует неравномерную нагрузку, но дороже);
- `guided` — порции уменьшаются по мере выполнения; `auto`, `runtime` (из `OMP_SCHEDULE`).

**Классы переменных:**
- `shared` — одна на всех (по умолчанию для переменных, объявленных вне параллельной области);
- `private` — своя неинициализированная копия у каждого потока (переменная цикла `for` и переменные, объявленные
  внутри области, — private автоматически);
- `firstprivate` / `lastprivate` — копия с начальным значением / значение последней итерации переносится наружу;
- `reduction(op: var)` — у каждого потока частичный результат, в конце они объединяются операцией `op`;
- `default(none)` — заставляет явно указать класс каждой переменной (хорошая практика).

**Синхронизация:** `barrier` (неявный — в конце `for`, `single`, `parallel`; снимается `nowait`), `critical`,
`atomic`, `ordered`, замки `omp_lock_t`.

**Прочее:** `collapse(n)` — объединить вложенные циклы в одно пространство итераций; `if(условие)` — распараллеливать
только при достаточной работе; `num_threads(n)`.

**Функции:** `omp_get_num_threads()`, `omp_get_thread_num()`, `omp_get_max_threads()`, `omp_set_num_threads()`,
`omp_get_num_procs()`, `omp_get_wtime()` (время по стенным часам).
**Переменные окружения:** `OMP_NUM_THREADS`, `OMP_SCHEDULE`, `OMP_PROC_BIND` (привязка потоков к ядрам),
`OMP_PLACES`.

**Компиляция:** GCC/Clang — `-fopenmp`; MSVC — `/openmp` (поддерживает только OpenMP 2.0: индекс параллельного
цикла должен быть знаковым `int`, нет `collapse` и задач) или `/openmp:llvm` (новее); CMake —
`find_package(OpenMP)` + `target_link_libraries(... OpenMP::OpenMP_CXX)`.

## 3. Что такое «автоматическое распараллеливание»

1. **Распараллеливание циклов директивами** (основная трактовка задания): программист только указывает, какой цикл
   параллельный (`#pragma omp parallel for`), а разбиение итераций по потокам, создание потоков и синхронизацию
   делает среда OpenMP. Противоположность — «ручное» распараллеливание: параллельная область, в которой работа
   делится вручную по `omp_get_thread_num()`, явные барьеры, задачи.
2. **Автоматическое распараллеливание компилятором**: компилятор сам находит циклы без зависимостей и распараллеливает
   их (GCC `-ftree-parallelize-loops=P`, Intel `-parallel`, MSVC `/Qpar`). Срабатывает только на простых циклах,
   для которых может доказать независимость итераций; на блочном Холецком, скорее всего, найдёт мало.

В обоих случаях ответственность за корректность (отсутствие зависимостей между итерациями) лежит на анализе
алгоритма — именно его спросят на защите.

## 4. Метрики параллельной программы

- **Ускорение** $S_P = T_1 / T_P$; **эффективность** $E_P = S_P / P$; **стоимость** $C_P = P \cdot T_P$.
- $T_1$ — время на одном потоке. *Относительное* ускорение — $T_1$ той же параллельной программы на одном потоке;
  *абсолютное* — $T_1$ лучшей последовательной программы (этап 2). В отчёте указать, какое используется.
- **Закон Амдала.** Если доля $\alpha$ работы выполняется только последовательно:
  $$T_P = T_1\Big(\alpha + \frac{1 - \alpha}{P}\Big), \qquad S_P = \frac{1}{\alpha + (1-\alpha)/P} \leq \frac{1}{\alpha}.$$
  Пример: $\alpha = 5\%$ → при $P = 4$ $S \leq 3{,}48$, при $P = 8$ $S \leq 5{,}93$, при $P \to \infty$ $S \leq 20$.
- **Закон Густафсона — Барсиса** (масштабированное ускорение): если с ростом $P$ растёт и задача, а $\alpha$ — доля
  последовательной части во времени параллельного счёта, то $S_P = P - \alpha(P - 1)$.
- **Сильная масштабируемость** — $N$ фиксировано, растёт $P$; **слабая** — работа на поток ($N^3/P$) постоянна.
- **Сверхлинейное ускорение** ($S_P > P$) возможно из-за кэша: у $P$ ядер в сумме больше L1/L2.
- Почему реальное ускорение ниже идеального: последовательные участки, накладные расходы (создание потоков, барьеры —
  единицы микросекунд), дисбаланс нагрузки, ограниченная пропускная способность памяти, снижение частоты Turbo Boost
  при загрузке всех ядер, Hyper-Threading.

## 5. Параллелизм в блочном методе Холецкого через блочные скалярные произведения

```
for j = 0 .. p-1:                        // последовательно: столбец j нужен всем следующим
    Ã_jj = A_jj − Σ_{k<j} L_jk L_jkᵀ     // модификация диагонального блока
    L_jj = chol(Ã_jj)                     // последовательно
    for i = j+1 .. p-1:                   // ← НЕЗАВИСИМЫЕ итерации: parallel for
        Ã_ij = A_ij − Σ_{k<j} L_ik L_jkᵀ  // цикл по k — редукция в один блок
        L_ij = Ã_ij · L_jj⁻ᵀ
```

**Какой цикл распараллеливать.**
- **Цикл по $i$** — итерации независимы: каждая пишет свой блок $L_{ij}$ и только читает уже готовые $L_{ik}$,
  $L_{jk}$, $L_{jj}$. Гонок нет. Это основной кандидат.
- **Цикл по $j$** — нельзя: шаг $j$ использует результаты всех предыдущих шагов.
- **Цикл по $k$** — слагаемые независимы, но суммируются в один блок: без `reduction` (для массивов — OpenMP ≥ 4.5)
  будет гонка данных; кроме того, параллельная редукция меняет порядок сложения и результат в последних разрядах.
- **Внутренние циклы по элементам блока** — слишком мелкое зерно: накладные расходы на fork/join сравнимы с работой.

**Зерно (гранулярность).** Итерация $i$ на шаге $j$ стоит $\approx 2b^3 j + b^3$ операций — для больших $j$ работы
много, для малых — мало. При малых $N$ выигрыша нет или он отрицательный ($S < 1$).

**Последовательная доля.** Модификация диагонального блока выполняется одним потоком. У диагонального блока
нужен только нижний треугольник: на шаге $j$ это $j$ блочных произведений по $\approx b^3$ операций, всего
$\sum_j j b^3 \approx N^2 b / 2$. Факторизация блоков добавляет $N b^2/3$. При общей работе $N^3/3$:
$\alpha \approx 1{,}5\, b/N$. Например, $N = 2000$, $b = 16$: $\alpha \approx 1{,}2\%$, и по Амдалу
$S_{12} \leq 1/(0{,}012 + 0{,}988/12) \approx 10{,}6$; при $b = 32$ — $\alpha \approx 2{,}4\%$, $S_{12} \leq 9{,}5$.
**Улучшение (стратегия `phases`):** модификации $\tilde A_{ij}$ не зависят от $L_{jj}$ — их можно посчитать в одном
параллельном цикле по $i \geq j$ (включая диагональный блок), затем последовательно факторизовать $\tilde A_{jj}$,
затем параллельно решить треугольные системы. Последовательной остаётся только факторизация:
$\alpha \approx (N b^2/3) / (N^3/3) = b^2/N^2$.

**Дисбаланс нагрузки.** На шаге $j$ всего $p - j - 1$ итераций; к концу их меньше, чем потоков, и часть потоков
простаивает. Внутри одного шага итерации одинаковы по стоимости (кроме последнего, неполного блока), поэтому
`schedule(static)` подходит; `dynamic` полезен, если блоки неравные.

**Накладные расходы fork/join.** `parallel for` внутри цикла по $j$ будит команду потоков $p$ раз (у `phases` —
$2p$). Среды OpenMP держат потоки в пуле, и запуск области стоит единицы микросекунд — при $N \geq 500$ это доли
процента. Альтернатива — одна параллельная область снаружи цикла по $j$, внутри — `#pragma omp for` (с неявным
барьером, который и обеспечивает зависимость «шаг $j$ закончен до шага $j+1$») и `#pragma omp single` для
диагонального блока; мы её не используем: это уже ручная организация работы, а выигрыш мал.

**Ложное разделение (false sharing):** два потока пишут в разные переменные, лежащие в одной строке кэша, и строка
«прыгает» между ядрами. У нас потоки пишут в разные блочные строки $L$ — разные строки кэша, проблемы нет. Типичная
ловушка — массив частичных сумм `sum[thread_id]`.

**Детерминизм.** При распараллеливании цикла по $i$ порядок операций внутри каждого блока не меняется, поэтому
результат **побитно совпадает** с последовательным, а погрешность — та же, что на этапе 2. Это удобная проверка
корректности.

**Информационный граф и ярусно-параллельная форма (ЯПФ).** Вершины — операции (блочные), дуги — зависимости по данным.
ЯПФ — разбиение вершин на ярусы так, что операции одного яруса независимы. Высота ЯПФ (число ярусов) — минимально
возможное время при неограниченном числе процессоров (длина критического пути), ширина — максимальное число
одновременно выполняемых операций. Для нашего алгоритма критический путь — $O(p)$ блочных шагов, ширина на шаге $j$ —
$p - j - 1$ блоков.

## 6. Как измерять

- Время — по стенным часам: `omp_get_wtime()` или `std::chrono::steady_clock` (у нас — `steady_clock` во всех
  сборках, чтобы `seq`, `omp` и `autopar` мерились одним таймером). **Не `clock()`**: в Linux он суммирует
  процессорное время всех потоков.
- Число потоков — `OMP_NUM_THREADS` или `omp_set_num_threads()`; печатать фактическое `omp_get_max_threads()`.
- Привязка потоков `OMP_PROC_BIND=close` / `spread` уменьшает разброс результатов.
- Повторы, минимум/медиана; на графике — $S(N)$ для $P = 2, 4, 8$ (и при необходимости $S(P)$ при фиксированном $N$).
- Ожидаемый вид: при малых $N$ $S < 1$ или около 1 (накладные расходы), с ростом $N$ $S$ растёт и выходит на плато
  ниже $P$; для $P$ больше числа физических ядер прирост маленький.

## 7. Типовые вопросы на защите

1. **Что такое OpenMP и модель fork–join?** (п. 2)
2. **Какие циклы вашего алгоритма можно распараллелить и почему именно их?** Цикл по $i$ — итерации независимы (п. 5).
3. **Почему нельзя распараллелить цикл по $j$? По $k$?** Зависимость по данным между шагами; редукция в один блок (п. 5).
4. **Что такое гонка данных? Как её избежать?** Одновременная запись (или запись + чтение) одной ячейки разными потоками
   без синхронизации; разные потоки должны писать в разные данные, иначе — `reduction`, `atomic`, `critical`.
5. **Какие переменные у вас private, а какие shared?** Матрицы $A$, $L$, размеры $n$, $b$ и номер столбца $j$ —
   shared (только читаются или пишутся по непересекающимся блокам); переменная цикла $i$ и все локальные переменные
   функций модификации и решения — private. Временного блока нет: $\tilde A_{ij}$ считается прямо на месте $L_{ij}$,
   и каждый блок пишет ровно одна итерация.
6. **Чем `static` отличается от `dynamic`?** (п. 2) Почему выбран ваш вариант? (п. 5)
7. **Закон Амдала. Какова последовательная доля у вас?** Теоретически $\alpha \approx 1{,}5\, b/N$ у `block`
   и $\approx b^2/N^2$ у `phases` (п. 5); оценка по замерам (подгонка закона Амдала) — п. 8: она больше, потому что
   включает накладные расходы и дисбаланс.
8. **Почему ускорение меньше числа потоков? Почему при малых $N$ оно меньше 1?** Накладные расходы, последовательная
   часть, дисбаланс, память, Hyper-Threading (п. 4).
9. **Почему при $P$ больше числа физических ядер ускорение почти не растёт?** На компьютере из отчёта 12 физических
   ядер и 24 логических процессора: два логических потока делят одно ядро и его вычислительные устройства (п. 1).
10. **Совпадает ли результат с последовательным?** Да, побитно — порядок операций в каждом блоке тот же (п. 5).
11. **Как измеряли время и что такое $T_1$?** (пп. 4, 6)
12. **Что такое false sharing?** (п. 5)
13. **Что будет, если скомпилировать без `-fopenmp`?** Директивы проигнорируются, получится последовательная программа.
14. **Что такое ЯПФ, высота и ширина графа алгоритма?** (п. 5)
15. **Чем сильная масштабируемость отличается от слабой?** (п. 4)
16. **Почему автопараллелизация компилятором не дала ускорения?** Компилятор распараллеливает цикл, только если
    докажет независимость итераций. У нас один массив $L$ и читается, и пишется через указатели, а внутренние циклы —
    суммирования; GCC распараллелил только генерацию тестовой матрицы (вне замера), остальные циклы отверг:
    «зависимость по данным между итерациями», «не удалось проанализировать зависимости» (п. 8).
17. **Чем стратегия `phases` отличается от `block` и почему она быстрее?** В `phases` модификация диагонального
    блока выполняется вместе с поддиагональными, последовательной остаётся только факторизация блока $b \times b$
    (пп. 5, 8).
18. **Почему $T_1 \approx T_{посл}$?** Код тот же, а запуск параллельной области на одном потоке почти ничего
    не стоит; поэтому относительное и абсолютное ускорения у нас почти совпадают.

## 8. Что получилось в нашей реализации

Числа — компьютер из отчёта (Xeon E5-2678 v3, 12 ядер / 24 логических процессора, Windows 11, MSVC 19.51,
OpenMP 2.0, $b = 12$), 03.11.2026. Подробнее — `README.md`, раздел «Результаты».

**Директивы.** Всё распараллеливание — три директивы `#pragma omp parallel for schedule(static)`:
```cpp
// block: для каждого столбца j
modify_block(jb, jb); factor_block(jb);                 // последовательно
#pragma omp parallel for schedule(static)
for (int ib = jb + 1; ib < p; ++ib) { modify_block(ib, jb); solve_block(ib, jb); }

// phases: для каждого столбца j
#pragma omp parallel for schedule(static)
for (int ib = jb; ib < p; ++ib) modify_block(ib, jb);   // включая диагональный блок
factor_block(jb);                                       // последовательно — только блок b×b
#pragma omp parallel for schedule(static)
for (int ib = jb + 1; ib < p; ++ib) solve_block(ib, jb);
```
Цикл по $j$ остаётся последовательным; неявный барьер в конце каждого `parallel for` гарантирует, что столбец $j$
готов до начала шага $j + 1$.

**Проверка.** При любом $P$ (в тестах 1, 2, 3, 5, 8, в том числе $P$ больше числа блоков) $L$ совпадает с однопоточной
побитно, `block` и `phases` — побитно между собой, сборка `seq` — побитно с `omp`; с эталоном этапа 1 — до $10^{-13}$.

**Ускорение.** Наибольшее — при $P = 8$: `block` — 1,88 ($N = 100$), 6,07 ($N = 1000$), 7,08 ($N = 3000$); `phases`
лучше — 6,73 и 7,45 при $N = 1000$ и $3000$. При малых $N$ на шаг $j$ приходится мало работы, и ускорение мало.
$T_1$ и $T_{посл}$ различаются не больше чем на 1,2 %, поэтому $S_{отн} \approx S_{абс}$.

**Модель распределения блоков.** Если время операции над блоком пропорционально числу её операций и накладных
расходов нет, время шага $j$ — последовательная часть плюс самая большая порция: `schedule(static)` отдаёт потоку
до $\lceil m/P \rceil$ из $m$ одинаковых блоков. Такая модель (`plot_speedup.py::static_schedule_speedup`) совпадает
с замерами при $P \leq 8$ в пределах 4 %: при $N = 3000$, $P = 4$ — 3,86 и 3,86, при $P = 8$ — 7,36 и 7,08.

**Закон Амдала.** По $P \leq 8$ у `block` $\alpha$ = 4,5 / 2,1 / 1,3 % ($N = 1000 / 2000 / 3000$) — столько же, сколько
у модели (4,4 / 2,0 / 1,3 %), и больше теоретической последовательной доли $1{,}5 b/N$ (1,8 / 0,9 / 0,6 %): эффективная
$\alpha$ включает и неравномерность распределения — на последних шагах блоков меньше, чем потоков, а порция
$\lceil m/P \rceil$ округляется вверх. Убывание $\alpha$ с ростом $N$ и преимущество `phases` — как в теории.

**Провал при $P = 12$.** На всех 12 ядрах ускорение меньше, чем на 8 (`block`, $N = 3000$: 6,44 против 7,08), — 60–71 %
от модели; при $P = 8 \dots 24$ суммарная производительность почти постоянна (17–22 GFLOP/s при $N \geq 1500$). Это не
алгоритм и не память (при $N = 1000$ матрица целиком в L3, провал тот же). Кандидаты — падение частоты при нагрузке
на все ядра и потоки, которые Windows ставит на одно физическое ядро; при барьере на каждом шаге $j$ самый медленный
поток задерживает всех (проверка — `README.md`, журнал, п. 11). При $P > 12$ (Hyper-Threading) ускорения не
прибавляется: два потока делят одно ядро.

**Автопараллелизация.** MSVC (`/Qpar`): ускорение 0,99–1,01 при $P = 2, 4, 24$; что распараллелено — по отчёту
компилятора (`results/autopar_report.txt`, после пересборки). GCC (`-ftree-parallelize-loops=P`, прогон в облаке):
ускорение 0,99–1,01. Компилятор распараллелил один цикл —
заполнение тестовой матрицы в `make_test_matrix` (вне замера). Остальные циклы отвергнуты (дамп прохода
`parloops`): 13 раз «зависимость по данным между итерациями», 8 раз «не удалось проанализировать зависимости»,
1 раз «скалярная зависимость между итерациями». Вывод: для этого алгоритма автоматического распараллеливания без
директив недостаточно — независимость итераций по блокам знает программист, а не компилятор.
