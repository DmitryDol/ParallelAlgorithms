## Варианты (делаем все по отдельности)

Трактовка задания не подтверждена (вопросы 4–5 в [README.md](../README.md#вопросы-преподавателю)), поэтому:

**Вариант А — директивы OpenMP над циклами** (сборка `omp`). Только `#pragma omp parallel for schedule(static)`:
распределение итераций делает OpenMP, без `omp_get_thread_num()`, задач и ручной синхронизации. Две стратегии:
- `block` — для каждого блочного столбца $j$: диагональный блок последовательно, затем **параллельно**
  поддиагональные блоки $i > j$ (модификация + треугольное решение целиком в одной итерации);
- `phases` — для каждого $j$: **параллельно** модификации всех блоков столбца, включая диагональный (они не зависят
  от $L_{jj}$), последовательно — только точечный Холецкий блока $b \times b$, затем **параллельно** треугольные
  решения. Последовательная часть меньше: $\approx N b^2/3$ против $\approx N^2 b/2$ операций у `block`.

Точечный алгоритм тоже распараллелен (элементы столбца ниже диагонали), но в замеры по умолчанию не входит.

**Вариант Б — автопараллелизация компилятором** (без директив; код тот же, OpenMP выключен):
GCC `-ftree-parallelize-loops=P` — число потоков задаётся при сборке, поэтому на каждое $P$ своя программа
`autopar_p<P>`; MSVC `/Qpar /Qpar-report:2` — одна программа `autopar`, число потоков — из `OMP_NUM_THREADS`.
Отчёт компилятора — в `results/autopar_report.txt`.

**Ускорение — оба определения:** относительное $S_{отн} = T_1 / T_P$ ($T_1$ — программа `omp` на одном потоке)
и абсолютное $S_{абс} = T_{посл} / T_P$ ($T_{посл}$ — последовательная сборка `seq`, то есть программа этапа 2
с теми же ключами оптимизации).

Сборки (ключи оптимизации у всех — как у сборки «с флагом» этапа 2):

| Сборка | GCC | MSVC |
|---|---|---|
| `seq` | `-O3 -march=native` | `/O2 /arch:AVX2` |
| `omp` | + `-fopenmp` | + `/openmp` (OpenMP 2.0) |
| `autopar_p<P>` / `autopar` | + `-ftree-parallelize-loops=P` | + `/Qpar /Qpar-report:2` |

В сборках без OpenMP директивы `#pragma omp` намеренно не действуют, предупреждение о них выключено
(`-Wno-unknown-pragmas` / `/wd4068`). Числа потоков для сборок GCC задаются параметром CMake
`LAB3_AUTOPAR_THREADS` (по умолчанию `2;4;6;8;12;16;24`).


`bench.py` по умолчанию:
- подбирает $b$ по последовательной программе при $N = 1000, 2000$ (не степени двойки) и использует его везде;
- $N = 100, 200, 300, 500, 700, 1000, 1500, 2000, 3000$ — без степеней двойки (конфликтные промахи этапа 2);
- $P = 1, 2, 3, 4, 6, 8, 12, 16, 24$ — до числа логических процессоров;
- автопараллелизацию меряет при $P = 2, 4$ и наибольшем $P$: ускорения от неё нет (см. ниже).

## Результаты (компьютер пользователя, перемер 09.11.2026)

Intel Xeon E5-2678 v3 (12 ядер / 24 логических процессора), Windows 11, MSVC 19.51, OpenMP 2.0 (`/openmp`; CMake
передаёт его как `-openmp` — это тот же ключ); фоновые программы закрыты. Числа — третий прогон (в `results/`);
первые два (03.11) занизила внешняя нагрузка при $P \geq 8$ — журнал, пп. 11, 14. Таблицы — `results/*.csv`,
графики — `results/*.png`.

- **$b = 12$** (подобран по `seq` при $N = 1000, 2000$: 0,114 и 0,900 с против 0,119 и 0,941 с при $b = 16$ этапа 2;
  на этапе 2 $b = 12$ не перебирался).
- **$T_1 \approx T_{посл}$:** $T_{посл} / T_1$ = 0,99–1,00, поэтому $S_{отн} \approx S_{абс}$.
- **Погрешность** при каждом $N$ одна и та же во всех сборках, при всех $P$, в обеих стратегиях и во всех прогонах
  ($8{,}9 \cdot 10^{-16}$ при $N = 100$ … $4{,}6 \cdot 10^{-14}$ при $N = 3000$).
- **До $P = 12$ (все физические ядра) ускорение ограничивает только алгоритм.** Модель распределения блоков
  (`static_schedule_speedup` в `plot_speedup.py`: время операции пропорционально числу её операций, накладных
  расходов нет, `schedule(static)` отдаёт потоку до $\lceil m/P \rceil$ из $m$ блоков шага) совпадает с замерами при
  всех $P \leq 12$ в пределах 2,2 % (`results/model.csv`, $N = 1000 \dots 3000$: 99–102 %). Замеры устойчивы:
  медиана выше минимума не больше чем на 1,3 % (в первых прогонах при $P \geq 8$ — до 34 %).
- **Наибольшее ускорение** — при $P = 12$ (при $N = 100$ у `phases` — при $P = 8$): `block` — 8,29 / 9,86 / 10,48
  ($N = 1000 / 2000 / 3000$; во втором прогоне при $N = 3000$ было 7,04), `phases` — 9,63 / 10,81 / 11,21;
  суммарная производительность при $N = 3000$ — 33,5 GFLOP/s (на одном потоке — 3,0). **`phases` быстрее `block`**
  при $P = 12$ и всех $N \geq 200$ (на 7–22 %), при $N = 100$ медленнее на 4 % (два барьера на шаге).
- **Закон Амдала** по $P \leq 12$ даёт у `block` $\alpha$ = 4,4 / 2,1 / 1,4 % ($N = 1000 / 2000 / 3000$), у модели —
  4,4 / 2,0 / 1,2 %. Это больше $1{,}5 b / N$ (1,8 / 0,9 / 0,6 %): к последовательной части добавляется
  неравномерность — на последних шагах блоков меньше, чем потоков, и $\lceil m/P \rceil$ округляет порцию вверх.
- **$P > 12$ (Hyper-Threading):** ускорения не прибавляется (`block`, $N = 3000$: 6,72 при $P = 16$ и 8,42 при
  $P = 24$ против 10,48); сильнее всего — провал при $P = 16$: на 4 ядрах по два потока, на 8 — по одному, а барьер
  ждёт самого медленного. При малых $N$ ускорение падает, при $N = 100$, $P = 24$ — ниже 1 (0,71).
- **Вариант Б (MSVC `/Qpar`):** $S_{абс}$ = 1,00 при $P = 2, 4, 24$ — ускорения нет, и отчёт компилятора
  (`results/autopar_report.txt`) объясняет почему: из 21 цикла `cholesky.cpp` не распараллелен ни один (C5012, ни одного
  C5011) — 19 раз «в теле цикла есть зависимость по данным» (код 1000), 2 раза «цикл не приводится к канонической
  форме» (код 506: внешние циклы точечного Холецкого — в `factor_diagonal_block` и `cholesky_point`, в их теле
  `checked_sqrt`, который может выбросить исключение). В отличие от GCC, MSVC не распараллелил и генерацию тестовой
  матрицы. Программа `autopar` выполняется последовательно, поэтому и `OMP_NUM_THREADS` на неё не влияет.
- **Сравнение с MPI (этап 4, тот же компьютер):** при $N = 3000$ и $P \leq 12$ время одинаково в пределах 3,3 %;
  OpenMP при $P = 12$ — 96–100 % модели этапа 4, MPI — 82–96 % (цена обменов; `lab4_mpi/README.md`).

Предварительный прогон в облачном контейнере (4 vCPU, GCC 13, $b = 32$; не для отчёта): `block` при $P = 4$ — 2,99
($N = 1000$), 3,59 ($N = 3000$); автопараллелизация GCC — 0,99–1,01, распараллелен только цикл генерации тестовой
матрицы (`make_test_matrix`, вне замера), в разложении все циклы отвергнуты: «между итерациями есть зависимость по
данным» (13), «не удалось проанализировать зависимости» (8).

### Проверка нестабильности при P ≥ 8

На компьютере пользователя, в PowerShell из корня репозитория (каждая команда — около 10 с). Во время первых двух
открыть «Диспетчер задач» → «Производительность» → «ЦП» и записать «Скорость» (текущую частоту):

```powershell
lab3_openmp\build\Release\cholesky_omp.exe -n 3000 -b 12 -t 8 -r 10
```
```powershell
lab3_openmp\build\Release\cholesky_omp.exe -n 3000 -b 12 -t 12 -r 10
```
То же при $P = 12$, но потокам разрешены только логические процессоры 0, 2, …, 22 — по одному на физическое ядро:
```powershell
$p = Start-Process lab3_openmp\build\Release\cholesky_omp.exe "-n 3000 -b 12 -t 12 -r 10" -NoNewWindow -PassThru; $p.ProcessorAffinity = 0x555555; $p.WaitForExit()
```
```powershell
powercfg /getactivescheme
```
Как читать: частота при $P = 12$ заметно ниже, чем при $P = 8$, — ограничение мощности или охлаждения (свойство
платформы, в отчёт); с маской время $P = 12$ заметно меньше и стабильнее — Windows ставила два потока на одно ядро;
ни то ни другое — фоновая нагрузка (посмотреть в «Диспетчере задач», какие процессы заняты).

**Итог:** проверка на программе MPI этапа 4 и перемер при закрытых программах (09.11.2026) показали третье —
внешнюю нагрузку: при $P \leq 12$ замеры совпадают с моделью, частота и размещение потоков ни при чём (журнал,
пп. 11, 14).

## Журнал

1. **Копия этапа 2.** Код скопирован из `lab2_cpp/src` (пространство имён `lab3`); этап 2 не менялся.
   Блок $\tilde A_{ij}$ по-прежнему вычисляется на месте $L_{ij}$, поэтому временных буферов нет и у каждого блока
   ровно один «писатель» — итерация параллельного цикла.
2. **TDD.** Сначала написаны тесты: при $P = 1, 2, 3, 5, 8$ (в том числе $P$ больше числа блочных строк, $N = 40$,
   $b = 16$, и $P$, не делящее его, $N = 129$) результат каждого режима **побитно** совпадает с $P = 1$, стратегии
   `block` и `phases` дают одинаковую $L$; разбор `-t` и `-m`. До реализации тесты не компилировались (нет режима
   `phases`). 4 намеренные ошибки распараллеливания — гонка (факторизация диагонального блока внутри параллельного
   цикла), неверный порядок фаз, параллельный цикл по зависимым столбцам точечного алгоритма, пропуск модификации
   диагонального блока — ловятся тестами в 3 из 3 запусков.
3. **Исключения вне параллельных областей.** Проверка положительной определённости (исключение) стоит только
   в последовательной части (факторизация диагонального блока, диагональ точечного алгоритма): исключение не может
   «вылететь» из параллельного цикла OpenMP.
4. **`schedule(static)`:** внутри одного шага $j$ итерации одинаковы по стоимости (кроме последнего неполного блока).
5. **Автопараллелизация GCC** (проверено до реализации): число потоков задаётся при сборке — `OMP_NUM_THREADS` на
   программу с `-ftree-parallelize-loops=4` не влияет, поэтому сборка на каждое $P$. Распараллелен только цикл
   генерации матрицы; причины отказов взяты из дампа прохода `parloops` (`-fdump-tree-parloops2-details`).
6. **Изоляция тестов этапов.** Модули этапов 2 и 3 называются одинаково (`programs`, `bench`, `plot_speedup`);
   при общем `uv run pytest` тесты получали модули чужого этапа. Исправлено хуком `pytest_collectstart`
   в корневом `conftest.py` (каталог этапа — первым в пути поиска перед импортом каждого теста), проверено при
   разном порядке каталогов.
7. **Подбор $b$** — по последовательной программе (как на этапе 2): в контейнере $b = 32$. Для параллельной
   программы оптимум может быть меньше: последовательная доля `block` растёт с $b$ ($\sim 1{,}5 b/N$); `phases`
   от этого почти не зависит.
8. **Помеха в замере контейнера:** у `phases` при $N = 3000$, $P = 4$ в замере 0,379 с ($S = 3{,}39$), повторный
   запуск дважды — 0,343 с ($S = 3{,}75$): все три замера (~1,1 с) попали на замедление виртуальной машины.
9. **Замеры на компьютере пользователя** (03.11.2026): 12 ядер, MSVC 19.51, OpenMP 2.0, $b = 12$; сверка и тесты

11. **Нестабильность при $P \geq 8$.** Первый прогон: при $P = 12$ ускорение ниже, чем при $P = 8$ (`block`,

    (тот же код и параметры): при $P = 12$ выше, чем при $P = 8$ (7,04 и 6,84; `phases` — 8,78 и 7,33), — 67–78 % от

    с точностью 2 % и совпадают с моделью в пределах 3 %, при $P \geq 8$ расходятся между прогонами до 36 %
    и остаются ниже модели; суммарная производительность при $P = 8 \dots 24$ — 16–26 GFLOP/s. Не память: при
