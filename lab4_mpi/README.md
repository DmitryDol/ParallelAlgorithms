## Алгоритм и распределение данных

Алгоритм тот же, что на этапах 1–3 (блочный left-looking через блочные скалярные произведения). **Блочная строка $i$
принадлежит процессу $i \bmod P$**: у строки $i$ работа $\sim i^2$, и при циклическом распределении каждый процесс
получает строки и из начала, и из конца матрицы (при распределении подряд последний процесс получил бы большую часть
работы). Процесс хранит только свои строки $A$ и $L$ и сам заполняет свои строки $A$ по формуле — рассылать матрицу
не нужно. На шаге $j$ строка $j$ нужна всем: её владелец рассылает её (`MPI_Bcast`), после чего каждый процесс считает
свои блоки $L_{ij}$, $i > j$. Две стратегии (те же, что на этапе 3, но с обменами):

- **`block`** — владелец строки $j$ считает $\tilde A_{jj}$ и $L_{jj}$, пока остальные ждут, и рассылает строку $j$
  целиком ($L_{j0}, \dots, L_{jj}$); затем все считают свои $\tilde A_{ij}$ и $L_{ij}$;
- **`phases`** — внедиагональная часть строки $j$ ($L_{j0}, \dots, L_{j,j-1}$) известна владельцу с прошлых шагов и
  рассылается сразу; все одновременно считают свои $\tilde A_{ij}$ (владелец — и $\tilde A_{jj}$); владелец разлагает
  $L_{jj}$ и рассылает только его ($b^2$ чисел); все решают треугольные системы. Последовательной остаётся только
  факторизация блока $b \times b$, но рассылок на шаге две.

Строка $j$ рассылается упакованной в непрерывный буфер $[L_{j0} \dots L_{j,j-1} \mid L_{jj}]$. Вместе с $L_{jj}$
рассылается признак ошибки разложения: если матрица не положительно определена, исключение бросают **все** процессы
на одном шаге, а не только владелец (иначе остальные ждали бы рассылки вечно). Погрешность каждый процесс считает по
своим строкам, затем `MPI_Allreduce(MAX)` — собирать $L$ не нужно (собирается только для проверок, `--dump`).

**Ускорение — оба определения** (вопрос 6 в [README.md](../README.md#вопросы-преподавателю)): относительное
$S_{отн} = T_1 / T_P$ ($T_1$ — программа `mpi` на одном процессе) и абсолютное $S_{абс} = T_{посл} / T_P$
($T_{посл}$ — программа `seq`: алгоритм этапа 2 без MPI с теми же ключами оптимизации). Вопросы 7–8: пока нет
ответа, замеры — на одном многоядерном компьютере, $P$ — до числа логических процессоров; точки при $P$ больше
числа физических ядер показывают эффект Hyper-Threading.

Время: барьер, `MPI_Wtime` до и после разложения, время замера — у самого медленного процесса (`MPI_Allreduce(MAX)`),
поэтому все процессы одинаково решают, сколько замеров делать; несколько замеров, в CSV — минимум и медиана.

## Установка MPI

**Windows (компьютер пользователя): Microsoft MPI** — два файла со страницы
<https://learn.microsoft.com/message-passing-interface/microsoft-mpi> (раздел «MS-MPI Downloads»):
`msmpisetup.exe` (среда выполнения и `mpiexec`) и `msmpisdk.msi` (заголовки и библиотеки для сборки). После установки
открыть новый терминал (установщики добавляют переменные `MSMPI_BIN`, `MSMPI_INC`, `MSMPI_LIB64`), проверить:

```bash
mpiexec -help
```

CMake находит MS-MPI сам (`find_package(MPI)`); если каталог сборки уже настраивался без MPI — удалить
`lab4_mpi/build` и запустить заново.

**Linux:** Open MPI (`sudo apt install openmpi-bin libopenmpi-dev`) или MPICH. В облачном контейнере (Ubuntu 24.04)
используется Open MPI: пакет MPICH 4.2.0 этой версии Ubuntu собран с PMIx и под своим `mpiexec` запускает
$P$ независимых процессов (у каждого размер коммуникатора 1). Open MPI не запускает процессы от root и больше
процессов, чем ядер, без ключей — скрипты добавляют `--oversubscribe` (только при $P$ больше числа ядер) и переменные
`OMPI_ALLOW_RUN_AS_ROOT*` (только под root) сами.

## Результаты (компьютер пользователя, 05.11.2026)

Intel Xeon E5-2678 v3 (12 ядер / 24 логических процессора), Windows 11, MSVC 19.51, MS-MPI 10.1.12498.52
(`MPI_Get_version` сообщает MPI 2.0); $b = 12$ (подобран по `seq`, как на этапе 3). Таблицы — `results/*.csv`,
графики — `results/*.png`.

- **Погрешность** при каждом $N$ одна и та же в обеих программах, при всех $P$ и в обеих стратегиях — и та же, что
  на этапе 3 при $b = 12$ ($8{,}9 \cdot 10^{-16}$ при $N = 100$ … $4{,}6 \cdot 10^{-14}$ при $N = 3000$).
- **$T_{посл} / T_1$** = 0,98–1,00 у `block` и 0,96–0,99 у `phases`: накладные расходы MPI при $P = 1$ малы.
- **Наибольшее ускорение:** `block` — 5,64 при $N = 1000$ ($P = 8$), 7,19 при $N = 3000$ ($P = 16$); `phases` — 5,97
  и 7,71. При $N \leq 1000$ лучшее $P$ — 8. **`phases` быстрее `block` при всех $N$** (при $P = 4$ и $P = 8$).
- **До $P = 4$ ускорение ограничивают алгоритм и обмены.** Замеры — 93–98 % от модели распределения строк без затрат
  на обмены (`results/model.csv`), при $P = 6$ — 87–96 %, при $P = 8$ — 82–92 %. Закон Амдала по $P \leq 4$: у `block`
  $\alpha$ = 7,0 / 2,4 / 1,7 % ($N = 1000 / 2000 / 3000$) при 3,7 / 1,9 / 1,3 % у модели — избыток и есть цена рассылок;
  он тем больше, чем меньше $N$ (отношение «вычисления / обмены» $\sim N / (P \log_2 P)$, теория, п. 6.2).
- **MPI и OpenMP (этап 3, тот же компьютер, рис. `mpi_vs_omp`):** при $N = 3000$ и $P \leq 4$ время одинаково
  в пределах 2 %, при $P = 8$ MPI медленнее на 12 %; при $N = 1000$ ускорение MPI ниже на 3–7 % уже с $P = 2$ —
  на обменах. При $P \geq 8$ сравнение в пределах разброса между прогонами (этап 3, журнал, п. 11: до 36 %).
- **$P = 8 \dots 16$:** при $P = 12$ — 53–64 % от модели; суммарная производительность — 16–22 GFLOP/s при любом
  $P$ от 8 до 16 (на одном процессе — 2,9–3,0), как у OpenMP на этапе 3 (16–26 GFLOP/s): ограничение — компьютер,
  а не способ распараллеливания. $P = 16$ здесь лучше, чем $P = 12$ (7,19 против 6,24 у `block` при $N = 3000$),
  на этапе 3 во втором прогоне — наоборот: такие различия — в пределах разброса.
- **$P = 24$ (все логические процессоры):** при малых $N$ программа сильно медленнее однопроцессной — в 33 раза при
  $N = 100$, в 1,9 раза при $N = 500$; при $N = 3000$ ускорение 5,07 (`block`) и 4,09 (`phases`) против 7,19 и 7,71
  при $P = 16$; медиана выше минимума до 60 %. Вероятная причина — процессов столько же, сколько логических
  процессоров, MS-MPI ждёт сообщений активным опросом, и любой поток Windows вытесняет какой-то процесс; рассылка
  на каждом шаге ждёт вытесненный процесс. У OpenMP (этап 3) при $P = 24$ такого обвала нет (0,79 при $N = 100$):
  ожидающие потоки там засыпают. Проверка — раздел ниже.

Предварительный прогон в облачном контейнере (4 vCPU, Open MPI 4.1.6, GCC 13, $b = 24$; не для отчёта): при $P = 4$
`block` — 3,07 / 3,62, `phases` — 3,29 / 3,72 ($N = 1000 / 3000$), 89–97 % от модели.

### Проверка: P = 12 и P = 24

По желанию, в PowerShell из корня репозитория (каждая команда — секунды):

```powershell
mpiexec -n 24 lab4_mpi\build\Release\cholesky_mpi.exe -n 100 300 500 -b 12
```
```powershell
mpiexec -n 23 lab4_mpi\build\Release\cholesky_mpi.exe -n 100 300 500 -b 12
```
Если при $P = 23$ (один логический процессор свободен для Windows) время в разы меньше, чем при $P = 24$, —
подтверждается вытеснение процессов при активном ожидании.

```powershell
mpiexec -n 12 lab4_mpi\build\Release\cholesky_mpi.exe -n 3000 -b 12 -r 5
```
```powershell
mpiexec -n 12 -affinity lab4_mpi\build\Release\cholesky_mpi.exe -n 3000 -b 12 -r 5
```
`-affinity` закрепляет каждый процесс за своим ядром: если с ним ускорение при $P = 12$ заметно выше — причина
провалов при $P \geq 8$ на этапах 3–4 в размещении процессов (потоков) операционной системой; если нет — в самом
компьютере (частота при нагрузке на много ядер; её видно в «Диспетчере задач» → «Производительность» → «ЦП»).

## Журнал

1. **Новая структура, а не правка этапа 3** (lab-mode: при переходе к распределённой памяти структура продумывается
   заново). Ядро скопировано из этапа 3 (пространство имён `lab4`), но операции над блоками теперь получают указатель
   на начало блочной строки и длину строки хранения: одни и те же функции работают с целой матрицей
   (последовательная программа), со своими строками процесса и с принятой строкой $j$. Порядок операций в блоке — как
   на этапах 2–3, поэтому результат совпадает побитно. Обе программы вызывают одни и те же скомпилированные функции
   ядра (библиотека `core`), поэтому совпадают побитно и с последовательной.
2. **Циклическое распределение строк** (теория, п. 6.1): блочная строка $i$ — у процесса $i \bmod P$; строки
   процесса хранятся подряд с длиной строки $N$, блок $ib$ начинается с локальной строки $(ib \operatorname{div} P)\, b$
   (неполным может быть только последний блок — он последний и у своего владельца). Каждый процесс сам заполняет свои
   строки $A$ по формуле.
3. **Две стратегии** — аналоги `block` и `phases` этапа 3: `block` рассылает строку $j$ целиком после разложения
   $L_{jj}$; `phases` — внедиагональную часть сразу (она известна с прошлых шагов, это «опережающая рассылка» из
   теории), затем только $L_{jj}$.
4. **Ошибка у одного процесса.** Исключение «матрица не положительно определена» возникает только у владельца
   строки $j$; если бы бросал только он, остальные ждали бы его рассылки вечно. Поэтому признак ошибки рассылается
   вместе с $L_{jj}$ (одно лишнее число), и бросают все процессы на одном шаге. Проверено тестом с ошибкой у процесса,
   отличного от 0.
5. **Замер времени.** Барьер, `MPI_Wtime`; время замера — максимум по процессам через `MPI_Allreduce`, поэтому решения
   о числе замеров (калибровка пачки, повторы до 1 с) все процессы принимают одинаково — иначе часть процессов
   вызвала бы разложение лишний раз и программа зависла бы на рассылке.
6. **TDD.** Тесты ядра и распределения (без MPI) — сначала, до реализации (не собирались); среди них главный для MPI:
   блоки, посчитанные по упакованной строке $j$, побитно равны посчитанным на месте. Тесты под `mpiexec` написаны
   после кода, поэтому их полезность проверена намеренными ошибками: треугольные решения до рассылки $L_{jj}$,
   владелец строки всегда процесс 0, без рассылки признака ошибки, своя строка $j$ среди строк ниже $j$ — все
   4 обнаруживаются (провал проверок или аварийное завершение). Граничные случаи: $N = 1$, $N < b$, $b = 1$, $P > p$
   (у части процессов нет строк: $N = 10$ и $40$ при $b = 16$), $P$, не делящее $p$ ($N = 129$, $b = 16$), $P = 7$
   больше числа ядер.
7. **MPI в контейнере.** MPICH 4.2.0 из Ubuntu 24.04 под своим `mpiexec` запускает независимые процессы (библиотека
   собрана с PMIx, а Hydra передаёт PMI-1: у каждого процесса `size = 1`) — заменён на Open MPI 4.1.6. Open MPI:
   под root нужны `OMPI_ALLOW_RUN_AS_ROOT*`, больше процессов, чем ядер, — только с `--oversubscribe`; ключ
   добавляется только при $P$ больше числа ядер, потому что с ним Open MPI перестаёт привязывать процессы к ядрам.
   Устаревшие привязки C++ отключены (`MPI_CXX_SKIP_MPICXX`) — нужен только интерфейс C.
8. **Изоляция этапов в общем `pytest`.** После появления этапа 4 два теста этапа 3 получили его модули `bench` и
   `plot_speedup`: они импортируют их внутри тела теста, а корневой `conftest.py` разводил одноимённые модули только
   при сборе тестов. Исправлено там же (хук `pytest_runtest_setup`) — новому этапу по-прежнему ничего настраивать
   не нужно; 167 тестов проходят при разном порядке каталогов.
9. **Замеры на компьютере пользователя** (05.11.2026): MS-MPI 10.1, MSVC 19.51, $b = 12$; сверка и тесты под
   `mpiexec` — перед замерами (`run_all.py`). Результаты — раздел «Результаты». Вычисления совпадают с этапом 3 до
   последнего разряда погрешности; до $P = 4$ — 93–98 % от модели без обменов.
10. **$P = 24$:** обвал при малых $N$ (в 33 раза медленнее при $N = 100$; $p = 9$ блочных строк, 15 процессов без
    строк, но в каждой рассылке участвуют все). Гипотеза — вытеснение процессов, ожидающих активным опросом, когда
    свободных логических процессоров не остаётся; проверка — $P = 23$ против $P = 24$ (раздел «Проверка»).
11. **$P = 12$ и $P = 16$:** у MPI $P = 16$ лучше $P = 12$, у OpenMP (этап 3, второй прогон) — наоборот; суммарная
    производительность при $P = 8 \dots 16$ у обоих — 16–26 GFLOP/s. Различия между такими $P$ — в пределах разброса
    между прогонами (этап 3, журнал, п. 11); проверка размещения процессов — `mpiexec -affinity`.
